# Requirements: Intervals.icu MCP — Climbing Training Loop

**Defined:** 2026-04-24
**Core Value:** Finish a climbing session → tell Claude → in one short conversation a complete activity (metadata + RPE) lands on Intervals.icu, and you can ask "how should I train tomorrow?" and get a data-backed answer that blends training load with wellness.

## v1 Requirements

Requirements for the current milestone. Each maps to a roadmap phase.

### Climbing Sessions

- [x] **CLIMB-01**: User can mark a planned calendar event as done; the tool creates a linked climbing activity on Intervals.icu while leaving the planned event on the calendar
- [x] **CLIMB-02**: User can create a climbing activity from scratch (no prior event, no Garmin sync) with date, duration, and title
- [x] **CLIMB-03**: User can enrich an existing activity (e.g. Garmin-synced) by activity ID — adds climbing metadata + RPE to an activity already in Intervals.icu
- [x] **CLIMB-04**: All climbing completion tools accept **discipline** (bouldering / sport lead / top-rope / trad, plus gym vs outdoor) as a parameter
- [x] **CLIMB-05**: All climbing completion tools accept **volume & grades** — sends and attempts — using Font scale for boulders and French sport scale for routes
- [x] **CLIMB-06**: All climbing completion tools accept **session focus** (power / endurance / technique / projecting / mileage)
- [x] **CLIMB-07**: All climbing completion tools accept an **RPE value (1–10)** and write it to the native `icu_rpe` field on the activity
- [x] **CLIMB-08**: Grade values are validated against the declared discipline — Font grades rejected on a sport route, French sport grades rejected on a boulder, with a clear error naming the expected scale
- [x] **CLIMB-09**: Activity-creation tools perform a duplicate guard (GET for an existing activity at the same date + type) before POST, preventing duplicate sessions on MCP reconnect or LLM retry
- [x] **CLIMB-10**: Custom-field writes are read-back-verified — if the intervals.icu custom field schema is missing, the tool surfaces a clear error instead of silently succeeding

### Wellness

- [x] **WELL-01**: User can log a wellness entry for a given date with subjective metrics (sleep hours, sleep quality, soreness, fatigue, motivation, stress)
- [x] **WELL-02**: User can log objective wellness metrics (HRV, resting HR) in the same tool call
- [x] **WELL-03**: Wellness writes use upsert semantics — fields not supplied in the call do not clobber values already logged for that day (e.g., a wearable-synced HRV survives a manual sleep entry)

### Training Status

- [x] **STAT-01**: User can ask for training status and receive a single report covering **today's readiness**, **weekly load review**, and **long-term trend** in one tool call
- [x] **STAT-02**: Report blends CTL/ATL/TSB + recent sleep + recent subjective soreness/fatigue + HRV/RHR
- [x] **STAT-03**: Report flags RPE data-quality issues — warns when a meaningful share of recent activities lack RPE so the user knows the readiness signal is noisy
- [x] **STAT-04**: Report output stays within ~400–600 tokens so the LLM retains headroom to reason on top of the data rather than parrot it

### Setup / Prerequisites

- [x] **SETUP-01**: README (or a dedicated setup doc) documents the exact intervals.icu custom fields the user must define in their athlete account (field names, types, example values) before the climbing tools can write them
- [x] **SETUP-02**: A verification path exists — either a dedicated diagnostic tool or a self-check at first write — that confirms the required custom fields are present in the athlete account and reports any missing ones by name

## v2 Requirements

Deferred to a future milestone. Tracked here so they aren't lost but not in the current roadmap.

### Climbing (v1.x enhancements)

- **CLIMB-v2-01**: Finger / skin condition captured as an explicit field (on the session record or as a wellness entry) — highest-value climbing-specific readiness signal not present in other fitness tools
- **CLIMB-v2-02**: Venue context (gym name / crag name) as a structured custom field to aid grade calibration over time
- **CLIMB-v2-03**: Grade-band volume aggregation in the status report — enables pyramid analysis (e.g., "last 4 weeks: V3 ×20, V4 ×8, V5 ×2")

### Scope expansion

- **GEN-v2-01**: Generic manual-activity creation for any sport (run, ride, swim, strength) — extend the create-activity tool surface beyond climbing
- **COACH-v2-01**: Lightweight coaching suggestions appended to the status report (e.g., "rest day" / "hard session OK" / "easy zone 2") driven by readiness thresholds

## Out of Scope

Explicitly excluded. Reasons documented to prevent re-adding without discussion.

| Feature | Reason |
|---------|--------|
| Multi-athlete support | Single user; adding coach-multi-athlete forces authz and data-scoping work for zero user benefit |
| Coaching / prescriptive plan generation (auto-writing next week's plan) | Out of scope in v1; if added, it's v2 as simple readiness-tier suggestions, not AI-generated plan authoring — the LLM already does that on top of the status report |
| Generic non-climbing manual activities in v1 | Climbing-first keeps v1 scope tight; generic support is v2 once climbing patterns settle |
| Per-problem / per-route structured tick list | Anti-feature — requires a list-type data model that flat Intervals.icu custom fields cannot represent cleanly; degrades the value of every other climbing record if half-done |
| Fingerboard / hangboard protocol tool | Anti-feature — v1 logs fingerboard as bouldering + `session_focus=fingerboard`; a dedicated protocol tool is scope creep until demand is proven |
| Historical PR tracking (lifetime best V-grade etc.) | Requires efficient historical custom-field indexing; defer until status tool proves useful and warrants the indexing work |
| Local shadow data store (SQLite, file-based cache) | Violates the "single source of truth = Intervals.icu" constraint; keeps the MCP server stateless and portable across machines |
| Custom-field *schema* creation via the tools | Intervals.icu API does not permit custom-field schema writes; field setup is a one-time user prerequisite |
| V-scale (bouldering) and YDS (routes) grade input | User climbs in Font + French sport; adding more scales expands the validator and error surface for no personal benefit. Trivial to add later if needed |
